# Preference Mining

Ported from Hermes 2026-09-24. The scripts are deployed to `~/.pi/agent/jobs/scripts/` and the
store lives in `~/.local/share/pi-jobs/preferences/`. Keep that deploy path: other skills call
`pref_log.py` there by absolute path.

A shared, domain-agnostic mechanism for turning "what the operator actually picks" into a
signal other skills and crons can read back later. It exists because this was first noticed as
a gap in `podcast-topic-discovery`: nothing recorded which shortlisted topic the operator asked to
have generated, so the next day's shortlist couldn't learn from it. The mechanism is generic on
purpose — any skill that offers a menu of options (podcast topics, coffee deals, GitHub issues
to triage, research candidates) can use it the same way.

## When to use this

**Log an event when:**
- A cron or skill just showed the operator a list of options (topics, articles, repos,
  products, anything with a title and ideally a URL) — log each shown item as `shown`.
- The operator picks one of a previously offered set, in this turn or a later one ("generate
  #2", "let's do the ROCm one", "yes to that repo") — log the pick as `chosen`.
- The operator reacts positively or negatively to something with no offered menu behind it
  (a thumbs-up/down, "I liked that one", "don't show me more of these") — log `liked`/`disliked`.

**Don't** invent your own tracking file for this inside another skill — use this one so
`pref_summarize.py`'s cross-domain view stays complete. A new domain name is free; just pick a
short, stable one (`podcast-topics`, `coffee-deals`, ...) and reuse it every time.

## How to log

```bash
# a single pick, like/dislike
python3 ~/.pi/agent/jobs/scripts/pref_log.py add --domain <domain> --action chosen \
  --title "<exact title as shown>" --url "<its URL, if it had one>"

# liked/disliked work the same way; keywords/tags are optional extras:
python3 ~/.pi/agent/jobs/scripts/pref_log.py add --domain <domain> --action liked \
  --title "..." --url "..." --keywords "rocm,agent" --tags "hardware"
```

For bulk "shown" logging (e.g. a discovery script logging everything it just printed), pipe a
JSON array on stdin instead — see `podcast_topics.py`'s `add-batch` call for a worked example:

```bash
echo '[{"title":"...","url":"...","keywords":["rocm"]}]' | \
  python3 ~/.pi/agent/jobs/scripts/pref_log.py add-batch --domain <domain> --action shown
```

You don't need to know or supply keywords for a `chosen`/`liked`/`disliked` event — if a
matching `shown` event exists for the same URL, `pref_summarize.py` inherits its keywords
automatically. Title + URL is enough; the store is append-only (`~/.local/share/pi-jobs/preferences/events.jsonl`),
so a wrong entry does not need editing, just don't repeat it.

**The number-reply case, specifically:** when a cron message ends with a numbered shortlist and
"reply with a number", and the operator later replies with just a number in that thread, match
it back to the item at that position in the earlier message (its title and URL are right there)
and log it as `chosen` before doing anything else with the pick. This is the case that motivated
the whole mechanism — don't skip it because the reply looks like "just a number".

## How to read what's been learned

```bash
cat ~/.local/share/pi-jobs/preferences/summary.md      # human-readable, per domain: leans toward/away, recent picks
cat ~/.local/share/pi-jobs/preferences/weights.json    # {domain: {keyword: score in [-3,3]}}, machine-readable
```

Both files are regenerated by `~/.pi/agent/jobs/scripts/pref_summarize.py` from the raw event log —
never edit them by hand, they're overwritten on the next run. Run it yourself
(`python3 ~/.pi/agent/jobs/scripts/pref_summarize.py`) if you want a fresh view mid-conversation rather
than waiting for whichever domain script happens to refresh it next.

A domain that wants the learned weights to actually change its behavior (not just be readable)
should shell out to `pref_summarize.py` and read `weights.json` itself, the way
`podcast_topics.py` does: run the summarizer, load `weights.json[domain]`, and add
`sum(weights.get(k, 0) for k in matched_keywords)` to whatever score already orders its
candidates. Wrap it in try/except — a missing or stale preference store should degrade to "no
bonus", never fail the actual task.

## Design notes (why it looks like this)

- **One shared JSONL log, not per-domain files.** A single `events.jsonl` keyed by a `domain`
  field means one summarizer serves every domain, and a new skill gets cross-domain visibility
  (via `summary.md`) for free instead of having to build its own.
- **`shown` is the denominator on purpose.** Without it, "chosen 3 times" can't be told apart
  from "chosen 3 out of 3 times it was ever offered" vs "3 out of 300" — the first is a strong
  signal, the second is noise. Not every domain can supply a `shown` set (a bare thumbs-down has
  no menu behind it); those domains just don't get keyword-weighted, which is a fine trade for
  simplicity — see `pref_summarize.py`'s docstring.
- **Decay (45-day half-life), not a permanent tally.** Interests move; a bulk of `chosen` events
  from two months ago should not permanently outrank what's actually being picked now.
- **File interface between producer and consumer, not a shared import.** `podcast_topics.py`
  runs `pref_summarize.py` as a subprocess and reads `weights.json` rather than importing it —
  keeps every consumer decoupled from the summarizer's internals, and means a broken summarizer
  degrades to "no bonus" rather than crashing the caller.
